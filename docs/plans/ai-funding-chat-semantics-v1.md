# Funding query semantics — v1

Version `funding-records-v1`. Local read-only source audit: `ai-funding-chat-source-audit.json`, generated by `scripts/funds/query_audit.ts` under `app_readonly`. Counts are a dated snapshot, not evergreen test expectations.

## Evidence and supported time bases

- ISUN: 82,309 project records, 47 programme codes; no event-date columns in the serving schema. The 15-column export parser has cumulative paid and duration but no signature/payment/completion dates. Event-date queries are unavailable on this corpus; programming period is supported independently. No date may be synthesized from duration, status, programme prefix or ingestion time. Adding a new source requires evidence and a separate ingest change; no authoritative detail-date corpus has been established by this audit.
- ISUN legacy parser maps empty money cells to zero. Consequently zero in the legacy serving corpus is a reported normalized value, not proof of a published zero. New analytics must expose this limitation and must not advertise a known-zero-paid predicate until raw observation provenance exists. Sums/ratios are explicitly on current normalized recorded values.
- DFZ: available financial years are 2015, 2016, 2017, 2021, 2022, 2023, 2024, 2025. A missing requested year is unavailable coverage, not zero payments. Source annual labels are used without translating them into calendar-day windows; no precise fiscal boundary is claimed. A record is an annual beneficiary/scheme record, not a bank transfer.
- Interreg: 1,251 operations in 2014–2020 and 708 in 2021–2027. All have start/end dates, but three older records have start after end. Start/end filtering reports source dates; overlap filtering treats reversed intervals as unknown and reports them. Source end dates are treated as inclusive calendar schedule dates (`start < queryEnd` and `end >= queryStart`); this is scheduled overlap, not historical administrative status. Signing and payment dates are unsupported.

## Populations, money and identity

- ISUN count unit: stable contract number. Distinct non-null EIK beneficiaries are separate from unidentified project records. Money bases: current recorded project cost, grant, own cofinance and cumulative paid. Paid/project cost and paid/grant are distinct ratio-of-sums measures, never averages of row percentages. Ratio denominator zero/null is unavailable; >100% is retained.
- DFZ default attributable population excludes payer EIK 121100421 from every denominator and amount. Gross-source totals are an explicit alternative. Legal-only means a verified corpus EIK; natural-person rows are not merged into verified people by names. Preserve negative corrections. Distinct beneficiaries across years are not summed annual distinct counts.
- Interreg operation unit is keep_id. Partnership unit is stable keep partnership ID (or operation/sequence fallback on a verified source key). Organisations use keep_partner_id and are not inferred from names/EIK availability. Bulgarian partnership means country OR country_department equals Bulgaria. Whole-operation money is counted only at operation grain; partner queries sum only own published budget or own EU contribution.
- Interreg partner publication states remain published, published_zero and unpublished. The audit found 21 unpublished Bulgarian budgets and 7 published zero budgets. Unpublished contributes missing coverage, not a fabricated zero. Never reconcile by scaling or equal-splitting whole-operation budgets.
- Numeric SQL sums use numeric casts with displayed rounding only at the boundary. Source columns are doubles, so answers do not claim source-accounting cent exactness.

## Classification and evidence

Use versioned existing programme, theme and political-link definitions; unknown code/identity remains unknown. ISUN EEA/Norway and RRP are distinct funding mechanisms. Legacy taxonomy's fallback 2014–2020 for unknown codes is not sufficient evidence for a new canonical period. Theme rules are editorial code/title inclusion, not exhaustive sector census. Beneficiary sector and project theme remain distinct.

Geographic project inclusion uses source confirmed locations without join multiplication. Partner seat and programme eligibility are not project implementation or allocated money. Location filters return whole matching project records with an explicit full-inclusion basis; allocated/per-capita money requires its own evidenced capability. Canonical Sofia aliases must round-trip.

Concentration/HHI and top-N shares recompute the full query population. Public-figure links use the canonical existing gates and current source state; name-based debarred overlaps remain name-based evidence. Missing linkage is not known absence where identity is unavailable. No procurement CRI, one-bid or funded-by relationship is inferred for grants.

The query and applied result carry population, catalog and source revisions. All supported constraints must execute or an explicit clarification/unavailable result replaces execution. Parent relations use entire cohorts and independent child periods. Cross-source money is displayed separately, with no automatic sum of costs, commitments and cash.

Independent fixture: `ai/tests/fixtures/funding-query.json`; arithmetic oracle: `ai/tests/fundingFixture.test.ts`. Synthetic dates/money are test data, not inferred production enrichment.

Cached-source follow-up: the actual `data/_cache/funds/projects.xlsx` export contains 82,309 rows and the same 15 headers; all four monetary columns have zero blank cells. This establishes observation coverage for that cached snapshot, not for arbitrary future zero-coercing loads. Step 2 must attach verified observation coverage only after matching source keys and values to the serving snapshot; invalidate it on source refresh. It enables known-zero predicates when verified, instead of permanently withholding a capability supported by source data.

Identity audit under the same repeatable-read snapshot: no null/duplicate serving key for ISUN contract_number, Interreg keep_id, partnership ID or DFZ id. All 12,120 partnerships have keep_partnership_id and keep_partner_id; 7,359 distinct source organisations exist. Interreg's enforced table PK is (keep_id, partner_seq), while the source partnership ID is presently complete/unique and is the preferred query identity. Current uniqueness is not a proof of reload stability: preserve source partnership IDs through loader reordering and test this; reject inconsistent IDs rather than silently merging. DFZ serial IDs are only revision-stable and cannot identify the same annual record across a truncate/reload. Queries may use them for pagination/details only with the matching data revision.
