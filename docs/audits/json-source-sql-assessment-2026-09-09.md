# SQL serving assessment for JSON-backed questions

Assessment date: 2026-09-09. This completes the source assessment in audit step 4; it does not claim SQL parity for sources without a database serving contract. Existing chat starters remain selectable. The SQL surface must continue to explain that no reviewed SQL adapter exists.

The accompanying JSON records the exact inspected files and SHA-256 hashes. These are local source versions, not production freshness evidence.

## Required gate before any SQL promotion

For each source, introduce its named serving contract and loader; retain source path, hash and reporting period; test an independently checked observation and missing-period case; compare the exact chat measure to SQL under `app_readonly`; and expose only the parameters the recipe supports. A stored JSON document alone is not evidence of measure parity.

The current implementation deliberately leaves these alternate SQL surfaces unavailable. No artificial menu entries, live HTTP calls embedded in SQL, or assertions of complete coverage were added. The normalized datasets already served by PostgreSQL were expanded in step 3 instead.

Relevant implementations: `ai/tools/people.ts`, `energy.ts`, `social.ts`, `tourism.ts`, `localDataset.ts`, `local.ts`, `localDetail.ts`, and `macro.ts`. Source hashes and individual loading/serving gaps are in `json-source-sql-assessment-2026-09-09.json`.
